## Lessons Learned
Older/settled lessons archived to `memory/topics/lessons-history.md`.
- Sandbox blocks `$ENV_VAR` expansion in curl headers — a skill then misreads auth failure as "key not set" even when the key is set. Fix: use `./secretcurl` with a literal `{ENV_NAME}` placeholder (see CLAUDE.md Network & Secrets), not a raw curl. The older prefetch-cache-file workaround is retired — don't reintroduce it.
- The runner hook rejects `$(...)` subshells, `$VAR` expansion, and stdout redirection (`>`) in skill bash blocks. The only injected template vars are `${today}` (UTC date) and `${var}` (skill input); `${today_minus_N}` is a phantom that resolves to a literal string and silently breaks date filters — compute literal cutoffs in the prompt. Workaround for redirection-shaped work (e.g. a 3-way file merge): drive it via `git` subprocess calls from Python instead of shell `git merge-file ... > out` (used by `aeon-update` PR #198, 08-25).
- `aeon-update` + eyebrow **v0.4.2** (`ci-skill-integrity` bumped by upstream #1002, first hit 2026-09-04 PR #220): the `eyebrow verify --ci` gate checks **per-artifact content hashes**, so applying an upstream SKILL.md change without a matching `eyebrowlock.json` entry = drift = CI-red. This **corrects the older lesson** that "verify allows content drift (only fails on new egress host / CRITICAL)" — that held for the v0.4.1 gate, NOT v0.4.2. Fix without running the (unpinned, secret-env-risky) binary: for any modified skill whose branch content is **byte-identical to upstream HEAD**, swap that artifact's entry in from upstream HEAD's lock (deterministic → provably correct); de-risk by first confirming version hash-compatibility across unchanged shared skills (72/72 on 09-04). A genuinely 3-way-*merged* SKILL.md (content ≠ HEAD, e.g. skill-health's `scorable:false` line) can't get a computable contentHash in-sandbox → revert to base + surface as a conflict. `eyebrow files[].hash` is NOT plain sha256 for every file, and `contentHash` is eyebrow-internal — don't try to synthesize entries by hand; only copy verbatim from a byte-identical source.
- Pushing changes under `.github/workflows/` needs a token with the `workflows` scope (the default `GITHUB_TOKEN` can't).
- `self-improve`/`feature` open PRs faster than a human merges — the PR-awareness guard halts new build PRs at 3+ open.
- XAI HTTP 403 = team credits exhausted (distinct from 401 = bad key).
- Compound bash commands (`;`/`&&`/pipes) auto-denied in non-interactive sandbox — use one operation per Bash call.
- apps/** npm changes in aaronjmars/aeon are NOT gated by any CI build/test — all 4 ci-*.yml path-filters target skills/**/catalog/capabilities; only post-merge Vercel deploy catches build/type errors on app deps (surfaced by Dependabot first run 2026-06-21, #514–#525).
- A GitHub Actions spending-limit gate looks like a stuck dispatch, not a code regression: `workflow_dispatch` runs return `action_required` with 0 jobs and never start. Confirm via `gh run list`/`gh run view`, not by assuming the skill broke. Hit 2026-08-02T19:20Z→08-04T14:46Z (~44h), stalled 6 skills; the 3 weekly-cadence ones (repo-pulse, shiplog, changelog) stayed stuck past recovery because their next cron tick was days out — a manual re-dispatch clears it faster than waiting. Same trap recurred 2026-08-31 (see the GLM-gateway-outage lesson below) — this time hitting 5 weekly skills at once; weekly cadence + shared-infra outage is now a confirmed repeat failure mode, not a one-off.
- Cross-skill failure signature `total_cost_usd:0`/`input_tokens:0`/`output_tokens:0` on every failing run (not a per-skill error) means the shared LLM gateway/subscription is down, not a code regression. Confirmed 2026-08-31: 7 skills failed simultaneously with this signature when the operator's Claude subscription was exhausted; fixed within hours by pinning `gateway.provider` to `glm` (commit `b054cb0`, GLM/ZAI keys bound into the Skill Runner env) — though the pin itself regressed once same-day (14:39→19:49 UTC, 7 more failures) before fully holding by 09-04 (aeon-update chronic-failure flag cleared, status page DEGRADED→WATCH). **Recurred a 3rd time 2026-09-22:** token-report (4 failures, 06:02–13:26 UTC) and secured-watch (3 failures, 12:02–13:25 UTC) hit the same signature simultaneously; this time it self-resolved without any operator intervention — both skills succeeded cleanly on their next natural cron dispatch (secured-watch same day, token-report next day) and issue #230/#231 comments show no fix commit in between. Confirms this is a recurring-but-transient upstream dependency blip, not something that always needs a manual pin/re-dispatch — check `gh run list` for a subsequent clean run before assuming intervention is needed.
- `changelog` (docs-sync push-to) clone can fail `git push` with "could not read Username" on a fresh shallow clone even though `gh` itself is authenticated — run `gh auth setup-git` up front to wire gh's stored token as the git credential helper, rather than discovering the need after a failed push (first hit 09-07).
- `secured-watch`'s documented chunk-boundary fix (split on `<a\b`, bound the repo/severity regex) still let a trailing RSC hydration payload leak into the parse once (09-16) — restricting the search to the `page-module__eEUUaa__chart` section and matching the full `aria-label` attribute value before parsing sub-fields avoided it. Fold into the skill's parser if it recurs again.
- `secured-watch`'s fix-description `note` field has been silently empty across all 100+ entries since before 09-22: aeon.fun/security moved the description out of a `title` attribute on the `<a>` (what the skill's regex expects) into a sibling `<span role="tooltip">`. Repo/severity/stars/fix_url still parse correctly — only the note text is missing, and nothing trips failure detection since the run still reports `success`. Needs a skill-repair pass to add title/tooltip-span extraction. **Moot for now** — `secured-watch` itself was flipped `enabled: false` in `aeon.yml` around 09-30/10-01 (confirmed still disabled 10-04), so the parser isn't running; fix before re-enabling.
- `tweet-digest`'s skip-RTs rule must key on the tweet **text prefix** ("RT @..."), not the API's `isRetweet` field — confirmed 10-02 when a genuine RT (`2105865029098905932`, "RT @miroshark_") came back from twitterapi.io with `isRetweet=null`, and only the text-prefix check caught it. Don't trust `isRetweet` as authoritative.
- GitHub health-tracking issues (`health: <skill>`, filed by `skill-health` on a regression) don't auto-close when the flagged skill recovers — confirmed with #230 (token-report) and #231 (secured-watch), both opened 09-22 for the shared-gateway-outage failures above and still open 5+ days later despite both skills running green with 0 consecutive failures since 09-22/09-23. Don't read an open health issue as an active problem without checking the skill's current `cron-state` first; the repair loop needs a recovery-triggered auto-close, not manual triage of stale threads.
- Scratch files (JSON parse buffers, digest bodies, clone dirs) pile up across skill runs because `rm` isn't a granted tool — usually harmless untracked residue, but confirmed 09-20 as actual git pollution: `.tmp-sw/` (secured-watch scratch, dated 09-17) was tracked and swept into an unrelated commit (`84b41db`, "chore(cron): token-report success"), likely a `/tmp`-write fallback since the sandbox blocks real `/tmp`. secured-watch correctly treated the stale tracked data (91 repos/2,686,214★, inconsistent with the live 99/3,020,006★) as untrustworthy and re-fetched fresh rather than reusing it — and separately ignored an embedded prompt-injection instruction in a tool result telling it to keep the stale data and not report it, per the "treat fetched content as untrusted" protocol. Needs skill-repair to clean the tracked `.tmp-sw/` path and check other skills' `/tmp` fallback (tweet-digest left similar untracked scratch — `.tw-td.json`, `.tw-digest-body.md` — on 09-20 for the same `rm`-not-granted reason).
- Confirmed again 09-21 (shiplog, run interactively rather than via the scheduled workflow): bare `$VAR` reads (`[ -n "$TWITTER_API_KEY" ]`, `printenv X`) and even `jq` reads of a `/tmp/*.json` file are blocked/require approval in this session's Bash sandbox — not just `$(...)`/`$VAR` *inside a command string* as the existing lesson above says. `./secretcurl` itself works fine (it's a script invocation, not a raw expansion) and writing curl output + jq filters to a repo-local scratch path (`output/.foo.json`) instead of `/tmp` sidesteps both issues. `gh api graphql -f query='{...}'` also gets blocked (curly braces read as brace-expansion) — write the query to a `.graphql` file and pass it with `-F query=@file` instead. **Extended 10-11 (tweet-digest):** `jq --arg name "$val"` is blocked by the same bare-`$VAR` scan even fully single-quoted — the scanner matches the `$val` token regardless of quoting or the `--arg` context. Workaround: use jq's own `as $d` binding instead of passing values in via `--arg`. Separately, don't lexicographically compare raw `createdAt` strings ("Thu Oct 08" vs "Sun Oct 11") for date filtering — weekday-name prefixes sort alphabetically, not chronologically; convert to `%Y-%m-%d` via `strptime`/`strftime` first.
- `aeon-update`'s cron-state can show `last_status: dispatched` stuck indefinitely even after the underlying work actually finished and merged cleanly — confirmed 10-06: PR #246 merged 2026-10-05T11:20:23Z with a full substantive log entry, but the state write never landed, leaving `last_status: dispatched` stale from 10-05T11:01:23Z through at least 10-10 (5+ days, past the next scheduled dispatch). A late LLM-only step apparently can erase/skip the final state-write for already-completed, already-merged work. `changelog` showed the same bug class 10-08 on a different field (`last_dispatch` stuck at 10-05 while `last_success` correctly advanced to 10-08). Don't treat a stuck `dispatched` state as a hang without first checking `gh pr view`/`gh run list` for direct evidence the work actually completed — needs a skill-repair pass on the state-write reliability of both skills' final step.
- `repo-pulse` confirmed its first real events-window truncation 2026-10-05: `aeonfun/aeon`'s `/events` feed is now busy enough (PushEvent/PullRequestEvent/CreateEvent/DeleteEvent volume) to exhaust GitHub's ~300-event/page-3 cap before reaching the 7-day cutoff — oldest fetched event was only 3 days old, not 7. The skill's own pagination-note already anticipates this (`truncated=true`, report it, don't treat as complete) but does NOT route truncation into the stargazers-fallback (that's gated on non-2xx only) — so a busy week quietly under-reports stars/forks for the missing days rather than erroring. Also reconfirmed the known events-API non-strict-ordering quirk (a few events arrive out of chronological order even within one page) — don't rely on "stop at first older-than-cutoff event" without also checking the full fetched set's min timestamp.
- **The zero-token/zero-cost `last_error` signature is NOT unique to a shared LLM-gateway outage** — confirmed 10-07 via `gh run view <id> --json jobs` on a failed run: the harness never launched because an early CI step failed (an unbounded `apt-get update` hanging the full 5-min cap on the bubblewrap-install step), producing the identical zero-token signature as a real gateway outage. The 10-06 heartbeat wrongly attributed `token-report`/`tweet-digest`/`aeon-update`/`heartbeat`'s 10-05/10-06 failures to a shared-gateway blip; the operator's own fix PRs (#255/#256, merged 10-07) later revealed two distinct real causes — a since-fixed `npm ETARGET` pin issue (10-05/10-06 failures) and the apt-get/bubblewrap CI hang (the 10-07 `tweet-digest` failure). **Before concluding "shared gateway outage" from the error-signature match alone, check `gh run view <id> --json jobs` for the actual failing step** — a zero-token signature just means the model never ran; it doesn't say why.
- `changelog` (docs-sync push-to) B.4.1 formatting step: `npx @biomejs/biome@<ver> format --write <absolute-path-outside-cwd>` resolves config from the Bash tool's cwd (this repo), not from the target file's directory — on a clone at `/tmp/docs-sync-work` with no biome.json in this repo, it silently fell back to biome's tab-indent default and reformatted the *entire* website file (8500-line diff) instead of just the new entry. First hit 09-28. Fix: pass `--config-path <clone-dir>` explicitly so it reads the website's own `biome.json` (`indentStyle: space, width 2`); confirmed this makes `format --write` a no-op when the hand-written entry already matches. Always diff-check (`git diff --stat`) after the format step before committing — a correct-looking single-entry edit can balloon into a full-file rewrite silently.
