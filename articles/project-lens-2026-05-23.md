# Every Plugin Registry Eventually Becomes A Trust List. Homebrew Got There In 2010.

In April 2024, a security researcher published a finding against Homebrew's official tap: twenty separate casks — including Google Chrome (260,000 installs that year) and Spotify (90,000 installs) — were downloading their payloads over plain HTTP with no integrity check, because each one had been written with the `no_check` flag set. The flag exists for a reason. Some upstream vendors push dynamic URLs whose checksums change too often to pin. The catch is that any of those download paths could be intercepted on a coffee-shop network and replaced with anything an attacker pleased, and the entire trust chain that Homebrew presented to the user — `brew install spotify`, friendly green checkmark — would happily run that replacement. Homebrew's response in the eighteen months that followed was not to scrap the tap model. It was to add build provenance via GitHub Actions attestations, a `brew verify` subcommand still in beta, and a slow rewrite of every blessed cask away from `no_check`. The model held. The trust contract got tightened around it.

That is the reason this paragraph is here: the AI agent industry, sixteen years after Homebrew introduced taps, is now publicly relearning what Homebrew already wrote down.

## What Homebrew actually built

A Homebrew "tap" is a third-party Git repository that contains formula files. Type `brew tap hashicorp/tap` and you have just added every Terraform-adjacent install path that HashiCorp maintains to your local install surface. The tap itself is not blessed. Homebrew's own documentation is explicit about what just happened: *"Installing from a tap is a trust decision for that tap. A tap can provide formulae, casks, external commands and tap metadata that install or run software, so using a tap means trusting its authors."* The distinction between `homebrew-core` (Homebrew's first-party tap, audited by a small team of maintainers) and any other tap is the entire shape of Homebrew's trust model. The package manager itself does not adjudicate. It moves the decision onto the user, and surfaces the distinction at the command line.

The reason this is interesting is that Homebrew did not start there. Early versions had no separation between core and third-party formulae. Taps were formalized around 2010-2012 in response to the obvious problem: as the formula count grew, no single maintainer team could vet everything, and the project either had to become a slower-moving curated registry or it had to externalize the trust decision onto the user. It picked the second. Sixteen years later, the same architecture survives because it is the only one that scales without a payroll.

## The 2026 wave is rebuilding the same thing

In May 2026 alone, three different layers of the AI agent ecosystem shipped what is structurally the Homebrew tap model under different names.

The first, and largest, is Anthropic's official MCP Registry. It launched in preview in the spring of 2026 backed by GitHub, PulseMCP, and Microsoft, and it is *explicitly* a metaregistry — it stores metadata, namespace claims, and verification status, but no code. Servers register under `io.github.username/server-name` (GitHub verification) or `com.yourcompany.*` (DNS verification). User-facing discovery is left to subregistries: Smithery, PulseMCP, Mastra, Glama.ai, MCP.so. The root authority verifies who you are; everything else is a downstream consumer's problem. This is the homebrew-core-plus-third-party-taps separation rebuilt for AI agents.

The second is the security audit nobody asked for. AgentSeal scanned 1,808 MCP servers earlier this year and found 66% had at least one security finding. Smithery, one of the most-used MCP discovery layers, had a path-traversal vulnerability — supply-chain compromise affecting a registry, not the packages inside it. The wave of attacks on agent registries in 2025-26 reads exactly like the npm and PyPI typosquatting and event-stream-style attacks of 2018-2022. The defenders rediscover signing, provenance, and namespace verification each time the registry layer is reinvented.

The third — and this is the lens — is the Aeon project, which shipped its tap-equivalent the morning of May 22 and its tap-listing-file the morning of May 23.

## What the Aeon registry looks like up close

On May 22, Aeon merged `./install-skill-pack <owner/repo>`. The CLI fetches a pack repo's default-branch tarball, parses a `skills-pack.json` manifest at the root, runs the existing `skills/skill-security-scan/scan.sh` against every declared `SKILL.md`, and either installs or prompts depending on what the scanner found. There is one allowlist file, `skills/security/trusted-sources.txt`, that gates the prompt: pack repos listed there auto-accept on clean scans, everything else falls into a HIGH-findings dialog or refuses without `--yes`. The first row added to that file was AntFleet's, in a one-line PR (`#211`) merged twenty minutes after the install protocol itself. AntFleet had been filing audit-bot PRs against the same repo for the previous four days. The auditor put itself on the auto-accept list. The maintainer let it.

On May 23 — this morning — Aeon merged `skill-packs.json` at the repository root, a machine-readable mirror of what had been a markdown table in the README. Five packs are listed: AntFleet (`trust_level: trusted`), baseddevoloper/aeon-skill-pack-vvvkernel, danbuildss/luca-aeon-skills, 0xShak/zer0-skill-pack, gitlawbounty/gitbounty-skill-pack. The `--list` flag on `install-skill-pack` now prints the registry without dragging in the install flow. The CLI reads the local file first and falls back to `https://raw.githubusercontent.com/aaronjmars/aeon/main/skill-packs.json` if the script is running outside a clone. A new entry in the publishing checklist requires every new pack PR to update both the README *and* the JSON in the same diff. That requirement existed implicitly the moment two surfaces were created; the checklist just made it explicit before the surfaces could drift.

The trust model is a near-verbatim port of Homebrew's. `trust_level: "trusted"` in the registry is a *discovery* hint — it tells `--list` to render a badge — but the actual scan-bypass behaviour is gated by `trusted-sources.txt`, the separate file that any pack maintainer has to send a PR against. The two cannot be unified, because that would let a registry edit forge a trust claim. The split is what makes the system safe to crowdsource. It is the same reason Homebrew never folded `homebrew-core`'s maintainer list into the formula schema.

## What's coming, on a sixteen-year delay

Three things are going to happen to the agent-registry layer over the next eighteen months, and Homebrew has already done all three.

The first is checksum drift. Right now Aeon's installer scans `SKILL.md` content but does not pin a commit SHA per installed skill. The first time a malicious pack maintainer updates a previously-clean skill *after* the trust review, that gap will fire, and the fix will be a `skills.lock` extension that pins commit SHAs and re-verifies on every `--update`. Homebrew added the bottle-attestation chain for the same reason in 2024 — the bottle that shipped this week is not necessarily the bottle the formula was reviewed against in 2019.

The second is the namespace squat. The MCP Registry's `io.github.*` namespace verification is not cosmetic. The first agent pack that mints a name colliding with a more-established project's release is the day Aeon's flat `owner/repo` keys grow a verification column. Homebrew solved this with the `homebrew-` repo-name convention and tap-promotion politics; npm solved it with scoped packages; PyPI solved it (badly, repeatedly) with manual de-duplication.

The third is the bypass class. AntFleet went on the trusted-sources list in one PR, on the same day the protocol shipped, with no out-of-band identity proof. That worked because AntFleet had already been filing audit PRs and the maintainer recognized them. It will not work the tenth time a stranger asks. The shape of the trust escalation — how much external evidence a pack maintainer has to produce before being added to `trusted-sources.txt` — is exactly the question every package registry has answered, and answered differently. Homebrew has the `homebrew-core` maintainer team. MCP has GitHub OAuth + DNS. npm has the org-verification flow. Aeon's answer right now is *the maintainer's judgement on the day of the PR*. It will need a written one.

The story worth noticing, sixteen years after `brew tap`, is that nobody is inventing a new architecture for this. The wave of 2026 agent registries — MCP's official metaregistry, Smithery and PulseMCP as user-facing subregistries, Aeon's `skill-packs.json` and its trusted-sources allowlist — is the same shape Homebrew arrived at by attrition. The interesting question is not *will Aeon's registry survive*. The question is which of the three failure modes above it ships a fix for first, and how long it takes the other two to make it onto the maintainer's queue.

The fact that nothing about this looks novel is the news.
