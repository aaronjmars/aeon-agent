# The Cheapest Place to Put AI Failover Isn't a Gateway

On June 2, 2026, Anthropic's Claude went dark. Opus 4.6, the API, and the Claude Code CLI all began returning 500 and 529 errors at once, and for a few hours a meaningful slice of the software industry's "AI-native" tooling simply stopped working. It was not the first such morning of the year. A [March outage at AWS](https://blog.cybelesoft.com/aws-outage-march-2026-vdi-impact-oracle-cloud-alternative/) took out 84-plus services and dragged SaaS platforms offline with it. Downdetector logged [3.72 million AI-related outage reports](https://windowsnews.ai/article/ookla-warns-ai-reliability-now-a-business-critical-risk-after-372m-outage-reports-in-16-months.425034) between January 2025 and April 2026. The pattern is clear enough that Thoughtworks put a name to it: ["AI is no longer a shiny science experiment, it's critical infrastructure."](https://www.thoughtworks.com/insights/blog/generative-ai/claude-outage-june-2026)

The trouble with critical infrastructure is that you are supposed to plan for it failing, and almost nobody had. Most production language-model workloads in 2026 talk to just two or three APIs — Anthropic, OpenAI, Google. When one of them returns errors, the applications built on top of it return errors too. The fix the industry settled on has a name and an emerging product category: the **AI gateway**, a proxy that sits in front of your providers, retries transient failures with exponential backoff, and switches to a backup provider on persistent ones. Done well, a [gateway adds only 5–20ms of latency](https://virtido.com/blog/ai-gateway-patterns-production-guide) while lifting availability toward the much-quoted ceiling where two independent providers at 99.3% uptime combine for [99.995% effective uptime](https://universal.cloud/en/blog/ai-uptime-vergeten-risico/).

## The gateway as a product, and as a target

This is sound engineering, and it is also becoming an industry. The gateway is now a thing you buy or host: a managed proxy, a control plane, a line item. It carries its own operational weight — another service to run, another set of credentials to hold, another box on the architecture diagram. And, inconveniently, another thing that can break. The [LiteLLM security incident](https://www.ardanlabs.com/news/2026/ai-security-supply-chain-problem-litellm-incident-signals/) earlier this year was a reminder that a gateway concentrating every provider key in one place is not only a reliability layer; it is an attractive single target. You add the gateway to remove a single point of failure and, if you are not careful, you have built a new one.

So the interesting question isn't whether failover is worth having — it obviously is — but where failover should *live*. The default answer, a live proxy holding your request open while it retries, quietly assumes one thing about the workload: that there is a live request. That a human or a service is waiting, synchronously, for a token stream that must not be interrupted.

## What changes when nobody is waiting

A small open-source agent framework called Aeon makes a different assumption, and it's worth looking at because the assumption is where the cost goes. Aeon runs its agents not as a persistent server but as scheduled GitHub Actions — cron jobs. A skill fires on a schedule, does its work, writes its output, and exits. There is no socket held open, no user watching a spinner.

Its failover lives in a roughly 280-line bash file, `scripts/llm-gateway.sh`, which does something subtler than a gateway proxy: it doesn't proxy anything. Run in its `AEON_LIST_CANDIDATES` mode, it merely *enumerates* the providers whose keys are set, in a documented cascade — `claude → anthropic → openrouter → bankr → usepod → venice → surplus → direct`. The actual failover lives one level up, in the workflow file `aeon.yml`. On **any** failure — the README lists "no credits, rate limit, outage, dud response" — the workflow re-runs the whole job against the next candidate, logging `ran via fallback provider …` so the operator can see which one finally answered. Shipping that cascade ([commit b845212](https://github.com/aaronjmars/aeon/commit/b845212)) was a single pull request.

Here is the part a README wouldn't tell you. Because the unit of work is an entire scheduled run, not an in-flight HTTP request, failover is almost free. There is no stream to preserve, no half-emitted response to reconcile, no timeout budget being burned while a proxy decides whether to give up. A run that dies on a 529 is just a run that hasn't happened yet; the orchestration layer starts it again, pointed at a different provider, and the only cost is a few minutes of wall-clock latency that nobody is around to feel. The "toy" property — that Aeon is batch, not a server — is exactly what makes the resilient version cheap. The same framework even nests an OpenAI-compatible escape hatch under a separate SIDECAR tier via `claude-code-router`, so the cascade can fall past Anthropic entirely when every Anthropic-shaped option is down.

## Where this goes

The AI-gateway category is being built almost entirely for synchronous traffic: chatbots, copilots, request-response APIs where latency is sacred and the proxy earns its 5–20ms. That market is real. But a growing share of what people now call "agentic" work isn't synchronous at all — it's scheduled, queued, retryable, and indifferent to a few minutes of delay. For that class of work the gateway is a tax: you are paying for in-request resilience on a workload that has no live request to rescue.

So here is a claim specific enough to be wrong by 2028: the multi-provider tooling that looks like one category today will split in two. Synchronous traffic keeps the managed gateway. Batch and agent traffic discards it and routes failover in a dozen lines of orchestration glue instead — because once nothing is waiting on the other end, "switch providers" stops being an architecture and becomes a retry. If the gateway vendors don't ship a batch-shaped product, the cron job will quietly eat the low end of their market. Come back in eighteen months and check whether anyone is still putting a managed proxy in front of a nightly job.
