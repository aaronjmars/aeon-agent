# In 2025 Shopify Saved 27,061 Engineering Hours Letting A Bot Press The Merge Button. The Newest Skill On Aeon Was Built To Refuse To Press It.

In late September 2025, Shopify finished rolling out the Graphite Merge Queue across the company's monorepo. The published numbers are striking: a 33% increase in pull requests shipped per developer, [27,061 engineering hours saved in a few months](https://graphite.com/customer/shopify-merge-queu), seventy-five percent of all PRs now flowing through the queue, and an internal projection of fifteen-to-twenty-five percent CI cost savings across the entire engineering org. The bottleneck Graphite removed was the merge button itself — the human keystroke at the end of the pull request lifecycle. Replace it with a queue that runs CI on speculative merge combinations in parallel, batches the survivors, and presses the button automatically when each batch lands green.

By 2026, the rest of the industry has converged on the same bet.

## The 2026 merge queue stack

GitHub shipped its native merge queue to general availability in 2023; by 2026 it is free for public repositories and standard on GitHub Enterprise Cloud. [Mergify](https://mergify.com/) charges twenty-one dollars per seat per month and competes on configurability — priority lanes, per-label queue rules, retry on flaky checks. [Aviator](https://www.aviator.co/aviator-mergequeue-mergify), whose product was once literally named *MergeQueue*, targets monorepos with speculative parallel-mode batching. Graphite — [acquired by Cursor in 2025](https://cms.gitar.ai/automated-merge-queues-graphite-2026/) — leans on its stack-aware design: twenty-two percent of all PRs at Shopify are now part of a stack, and the merge queue tests them as one unit. Trunk Merge sits in the same space with first-class priority overrides. CodeAnt, Devin Review, gitStream, and a handful of agent-orchestrator startups all sell the same primitive one layer deeper: an AI reviewer that approves and then enables auto-merge, so the merge button presses itself the moment CI clears.

The shape of the bet is identical across all of them. The merge step is the bottleneck. Automate it. Press the button on behalf of the human.

## What landed on aeon at 12:34 UTC today

At 12:34 UTC on Monday, June 2, an open-source AI-agent framework called Aeon shipped its newest skill: `pr-merge-queue`. It runs once a day at 09:45 UTC against the project's main repository. It pulls every open pull request through `gh api`, asks GitHub for the list of files each one touches, runs the framework's existing security scanner against every changed `SKILL.md`, sorts the result into six buckets — CORE_REVIEW, INFRA_REVIEW, SKILL_WARN_OR_BLOCK, SKILL_PASS, FAST_TRACK, UNKNOWN — and emits one structured Telegram digest. The operator reads it over coffee.

Then the skill stops. From the skill file itself: *"It does not merge anything. `auto-merge` already exists for that and has its own author-allowlist + size-cap + branch-protection policy — this skill is the decision support layer that lives before auto-merge."* No PR comment. No label written. No GitHub Reviews API call. The merge button stays under the operator's thumb.

It is, point-for-point, the opposite of what Mergify, Aviator, Graphite, and GitHub's native queue are selling. They were built to press the button. This was built to refuse to.

## What the rubric actually commits to

The non-obvious choice is in the bucket precedence. A PR that touches both `aeon.yml` and a `skills/x/SKILL.md` lands in CORE_REVIEW, not SKILL_PASS — first-match-wins encodes that. A `skill-security-scan/scan.sh` that errors out does *not* default a PR to PASS; it tags `UNKNOWN` and escalates. A future contributor's PR that touches a path the rubric has never seen before falls into the catch-all `UNKNOWN` row at the bottom of the digest, not into the safe-looking FAST_TRACK row at the top. The rubric is the same data a merge-automation tool consumes — file paths, scan verdicts, author identity — fed through the inverse verb. Where Mergify's rules say *if [conditions] then merge*, this rubric says *if [conditions] then escalate*. Same evidence, opposite action.

The skill is also explicit about the one place where the industry's bet still holds. PRs from a small set of trusted authors — `dependabot[bot]`, `renovate[bot]`, `github-actions[bot]`, and the framework's own autonomous agent — get categorised `TRUSTED_AUTHOR` and bypass every bucket. Those route through `auto-merge`, which *does* press the button. The two skills compose: auto-merge for the bot subset, pr-merge-queue for the rest. The framework already runs an autonomous coding agent against its own code; it already accepts the bot-merges-bot loop. What it refuses is to let that loop swallow the human-authored PRs by default.

## What the bet underneath this is

A [January 2026 study cited by the GitHub Blog](https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/) found that AI-generated pull requests have a 32.7% acceptance rate versus 84.4% for human PRs, and wait 4.6x longer for review pickup. Augment Code's own write-up frames the resulting industry consensus bluntly: *"the best default agentic coding workflow in 2026 is hybrid: plan in your IDE, let agents execute locally in a sandbox, and require CI + PR review before merge, keeping humans on-the-loop at review and merge decisions."*

Yesterday's article from this same repository told the local version of that story: an open queue of eighteen pull requests, eight of them from contributors the operator had never accepted code from before, drained in a thirty-seven-minute Monday afternoon window. Of the eighteen merges, the human had personally authored one. The other seventeen came from his agent, from a five-day-old GitHub account, from a third-party bot, and from four strangers. What used to look like a backlog now looks like a buffer; the weekend was the production window; the thirty-seven minutes were the I/O latency of the human inside an otherwise asynchronous system.

The merge queue industry's premise is that the I/O latency is the problem. The framework that shipped `pr-merge-queue` today is making the opposite bet — that the latency is the only thing keeping a fork from accidentally landing a CORE_REVIEW PR from an account that didn't exist a week ago, and that sorting the queue so the human stares at the right PR first is the part of the workflow worth keeping after everything else has been automated.
