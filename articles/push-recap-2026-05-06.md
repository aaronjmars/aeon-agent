### Show HN dispatch timing: the alert that times the launch
**Summary:** Closes the lead-time gap between "the Show HN draft is pre-written" (PR #151, May 1) and "it's time to dispatch it." The agent has been carrying a ready-to-paste launch post for five days while sitting at ~270⭐ with the 300⭐ milestone ~30 stars out at a ~4/day pace; without an early signal the milestone passes reactively and the Show HN dispatch lands on a Sunday by accident. This skill reads the last 14 days of `memory/logs/YYYY-MM-DD.md` repo-pulse blocks, builds a stargazer time series, and projects the milestone-crossing date by linear extrapolation off the 7-day rolling average — alerting only when both gates fire (projected date 7–14 days out AND lands on Tue/Wed/Thu).

Gate logic: alert fires only if `7 ≤ days_to_target ≤ 14` AND `projected_date.weekday() ∈ {Tue, Wed, Thu}` — the same Tue/Wed/Thu launch window the operator's existing `show-hn-draft` checklist already specifies. Linear extrapolation only — no regression, no exponential model, no S-curve fitting; goal is to convert today's pace into a date, not to forecast trajectory shape changes (the assumption being that Show HN cadence on a small-fleet repo doesn't merit complex modelling). Per-`(repo, milestone)` dedup with 7-day re-emit window via `memory/topics/star-momentum-state.json`: once an alert fires for a `(repo, target_milestone)` pair, it stays silent for 7 days; if 7 days pass and the milestone still hasn't crossed and the projection still lands in-window on Tue/Wed/Thu, the alert re-fires as a periodic reminder. ### Dashboard hardening: shell injection defense-in-depth
**Summary:** Mirrors PR #150's earlier fix on a sibling dashboard endpoint — `dashboard/app/api/skills/[name]/run/route.ts` was building a `gh workflow run` command via string concatenation and shipping it through `execSync`, meaning user-supplied `var` and `model` values traversed a shell. The whitelist strip already neutered metacharacters so this isn't a live exploit, but the round-trip through bash was the wrong primitive for the job.

**Commits:**
- `89d566b` — fix(dashboard/skills/run): use execFileSync to harden against shell injection (#158) — merged 2026-05-06 01:02 UTC
  - Modified `dashboard/app/api/skills/[name]/run/route.ts` (+5, -5). Swaps `import { execSync }` for `import { execFileSync }`. Drops the `JSON.stringify(skillVar)` / `JSON.stringify(model)` shell-quoting that was only there to escape into bash; `execFileSync` receives the args as a `string[]` array directly to `gh`, so quoting is a no-op. The build-up logic switches from `cmd = \`gh workflow run aeon.yml -f skill=${name}\`` (+ string concat) to a structured `args = ['workflow', 'run', 'aeon.yml', '-f', \`skill=${name}\`]` (+ `args.push('-f', \`var=${skillVar}\`)`). `cwd: REPO_ROOT` and `stdio: 'pipe'` preserved.

**Impact:** Defense-in-depth, not a vulnerability close. The PR description explicitly notes that the existing whitelist strip already neutered metacharacters, so this is a primitive change ("we shouldn't be invoking a shell here at all") rather than a security incident response. The pattern is now consistent across both dashboard skill-run endpoints (PR #150 hardened the `dashboard/app/api/skills/run` endpoint earlier; this completes the cleanup). Worth noting because it's a small, principled edit — the kind that catches the next bug rather than the current one.
