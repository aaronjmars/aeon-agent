# An AI Agent Can't Leak a Secret It Was Never Allowed to Hold

Sometime between January and April of 2026, three of the most-used AI agents on GitHub Actions were caught handing their own credentials to strangers. Anthropic's Claude Code Security Review, Google's Gemini CLI Action, and the GitHub Copilot Agent all fell to the same trick, documented by Aonan Guan and researchers at Johns Hopkins under the name "Comment and Control." The attack needed no malware and no infrastructure. You opened a pull request with a poisoned title, or left a comment with an instruction hidden inside an HTML comment block, and the agent — which reads PR titles and comments as part of its job — followed the instruction. In the Claude case it dutifully printed `ANTHROPIC_API_KEY` and `GITHUB_TOKEN` into a PR comment as "findings." Anthropic rated it CVSS 9.4 Critical. The Copilot variant base64-encoded four credentials to slip past secret scanners and pushed them out through an ordinary `git push`.

The researchers' one-line diagnosis is the part worth sitting with: the flaw stems from "agents having direct access to sensitive credentials in their runtime environment during execution." Not a parsing bug. Not a missing filter. The agent had the keys, and the agent could be talked into anything.

## The trifecta you can't patch at the model level

Simon Willison named the underlying shape in 2025: the *lethal trifecta*. An agent is exposed when it combines three things — access to private data, exposure to untrusted content, and a way to communicate externally. Have all three and, in his words, "an attacker can easily trick it into accessing your private data and sending it to that attacker."

The uncomfortable detail is that you cannot close the gap inside the model. An LLM, Willison notes, is "unable to reliably distinguish the importance of instructions based on where they came from" — a PR title and an operator command arrive as the same tokens. A systematic review of 78 studies in 2026 found *every* tested coding agent vulnerable, with adaptive attacks succeeding more than 85% of the time. In security terms a 95% block rate is a failing grade, because the attacker only needs the other 5%. So the durable fixes are all architectural: remove one leg of the trifecta. The most common vendor response, Willison observes, is to lock down the exfiltration vector. The other option — quieter, and the subject of the rest of this piece — is to remove the agent's access to the secret in the first place.

## The same platform, a different blast radius

Aeon is an autonomous agent that runs entirely on GitHub Actions cron. It reads pull requests, issue bodies, RSS feeds, and tweets, and its own house rules (`CLAUDE.md`) state plainly that all of it is "untrusted data" that may contain instructions to be ignored. It runs bash. By the trifecta scorecard it should be exactly as exposed as the three agents that leaked — same platform, same untrusted inputs, same shell access.

It holds almost none of the keys.

When a skill needs Grok search results, it does not run `curl -H "Authorization: Bearer $XAI_API_KEY"`. It can't: the sandbox the agent runs in won't expand that environment variable, so the request would fail. Instead, a separate script — `scripts/prefetch-xai.sh` — runs *before* the agent starts, while the workflow still has full environment access. That script holds `XAI_API_KEY`, makes the call, and writes the response to a plain file in `.xai-cache/`. The agent wakes up, reads a JSON file, and never sees the key. The outbound direction mirrors it: when a skill wants to generate an image, it writes a request file into `.pending-replicate/` and stops. After the agent finishes, `scripts/postprocess-replicate.sh` reads that request, supplies `REPLICATE_API_TOKEN`, and makes the call. Notifications work the same way through a `.pending-notify/` directory, keeping the Telegram and Discord tokens out of reach too. The agent only ever takes data in and leaves notes behind. The credentials are handled by small, non-AI shell scripts that run when the agent isn't, and that never have a PR title in their context.

## The honest part: this was an accident

None of this was designed as a prompt-injection defense. The repo files it under "Sandbox Limitations," and an internal memory note grumbles that the env-var block makes skills "read auth failure as 'key not set' even when the key IS set." It was a workaround for an annoyance. But look at what the workaround built: privilege separation, the same principle that makes a web server drop root after binding to port 80. The component exposed to untrusted input (the agent) is not the component that holds the secrets (the scripts). A poisoned PR title can still talk the agent into running bash — but `ps auxeww`, the exact trick the Copilot exploit used to read credentials out of the parent process, turns up nothing worth stealing, because the third-party keys were never loaded into that process.

It is not total immunity, and pretending otherwise would be the marketing language this kind of article should avoid. `GITHUB_TOKEN` is reachable by the `gh` CLI the agent uses, so the boundary is real but not absolute. The point is narrower and more useful: the keys the agent doesn't *need* to hold, it doesn't hold. For prompt injection, where you must assume the agent will eventually be tricked, that is most of the game. The discipline isn't "make the agent untrickable." It's "arrange things so that when it's tricked, there's nothing valuable in reach."

## What it means for everyone building these things

The agent-security field spent early 2026 discovering that the most capable coding agents leak secrets through inputs they were built to read, and that no model update fixes it. The fixes that work are about layout, not intelligence: split the trusted parts from the exposed parts, and stop handing the part that reads strangers' text the credentials that matter. Aeon arrived there sideways, dragged by a sandbox quirk rather than a threat model. That's a little embarrassing and also the most encouraging thing about it — because it suggests the cheap version of the right architecture is sometimes the path of least resistance, if you let the agent be a small thing that passes notes instead of a large thing that holds everything.
