### 3. RSS/Atom feed column (minitor)
**Type:** Integration
**Effort:** Medium (1–2 days)
**Impact:** Minitor has 49 column types covering GitHub, HN, Reddit, DEV.to, Bluesky, DeFiLlama, CoinGecko, and more — but no generic RSS/Atom reader. Every blog, changelog, paper alert service, podcast feed, and news site publishes one of these formats. A single column type that accepts any feed URL would add more breadth than the next 20 individual integrations combined. It's keyless by definition (RSS is a public pull format), fits minitor's zero-auth design contract exactly, and is the most-requested generic input format in monitoring tools broadly. The SIGNA network, LiquidPad, and every other project in ECOSYSTEM.md that has a blog publishes an RSS feed — this unlocks them all.
**How:**
1. Create `lib/integrations/rss.ts`. Fetch the given URL; detect format from root element (`<rss>` → RSS 2.0, `<feed>` → Atom 1.0); normalize to flat item schema `{id, title, url, description, publishedAt, author}`. RSS field map: `<guid>` → id, `<link>` → url, `<description>` → description (strip HTML tags), `<pubDate>` → publishedAt, `<author>` or `<dc:creator>` → author. Atom field map: `<id>` → id, `<link href="...">` → url, `<summary>` or `<content>` → description (strip HTML), `<published>` → publishedAt, `<author><name>` → author. Apply SSRF guard identical to webhook validation: block RFC-1918 / loopback / localhost URL prefixes (feed URL is operator-set, but SSRF protection is still appropriate).
2. Create 3-file plugin (`components/columns/rss.tsx`, type registration, integration helper). Column config: `feedUrl` (required, validated https:// URL at save time), `limit` (5–25, default 10). Column item: domain favicon + title + description clip (150 chars) + author (if present) + relative time + external link. `#ee802f` RSS orange accent, `Rss` lucide icon (already in lucide-react). Parse XML using DOMParser (works in both browser and Node 18+ without extra dependencies).
3. Register in column type registry. Update README: add RSS to the keyless/no-token-required column list, bump count 49 → 50. Add `DeckTemplateColumn.feedUrl?: string` to `lib/deck-templates.ts` so future starter templates can include RSS columns. No new npm dependencies.

**Effort:** Medium (1–2 days)

A triage skill with `var: PR_NUMBER` produces a structured PR comment in under 60 seconds: security scan verdict for each SKILL.md, required secrets enumeration, cron schedule conflict check against existing aeon.yml, basic quality signals. Human still makes the merge decision — the skill surfaces the facts so the decision takes 10 seconds instead of 10 minutes.

Step 1: fetch PR metadata via `gh api repos/aaronjmars/aeon/pulls/${PR_NUMBER}` — author, created_at, head SHA, changed file paths. Step 2: identify all `*/SKILL.md` files in changed paths; download each via `gh api repos/aaronjmars/aeon/contents/{path}?ref={head_sha}` (base64 decode to temp file). Step 3: run `skills/skill-security-scan/scan.sh` against each downloaded SKILL.md. Step 4: for each SKILL.md, parse: frontmatter fields (name, description, tags, schedule/var), required secret variable names (grep `\$[A-Z_]{4,}` patterns outside of `./notify` and `gh api` contexts), step count, presence of a `./notify` call.
2. Compare each SKILL.md's cron schedule against existing `aeon.yml` schedule entries to detect slot conflicts. Compose a structured comment body: per-file security scan table (PASS/WARN/BLOCK + specific HIGH findings if BLOCK), required secrets list (operators need to provision these), cron conflict warnings (if any), quality checklist (description ✓/✗, ≥3 steps ✓/✗, notify call ✓/✗, tags present ✓/✗). Post via `gh pr comment ${PR_NUMBER} --body "..."`.
3. Exit taxonomy: TRIAGE_OK (comment posted successfully), TRIAGE_NO_SKILLS (PR has no SKILL.md changes — post a brief "no skill files changed" note), TRIAGE_PR_NOT_FOUND (invalid PR number — exit non-zero), BAD_VAR (PR_NUMBER empty). Register in skills.json with `tags: [dev, community]`.

### 5. Deck version history (minitor)
**Type:** Feature
**Effort:** Medium (1–2 days)
**Impact:** Operators who have built up a minitor deck with 10–15 columns over weeks have one unrecoverable failure mode: accidentally removing or misconfiguring a column. The export/import flow requires them to remember to export first — it's a manual backup that nobody does until they need it. Deck version history makes recovery automatic: every time the deck is mutated (column added/removed/reordered, config saved), a snapshot is silently captured. The last 5 snapshots surface in the Configure dialog as a "Version history" section — one click restores any prior state. The serialization format (DeckExport v1 JSON) already handles everything; this is purely a persistence layer and a small UI surface on top of the existing export contract.
**How:**
1. New migration for `deck_snapshots` table: `id` serial PK, `deck_id` integer FK → decks.id ON DELETE CASCADE, `snapshot_json` text (full DeckExport v1 JSON), `captured_at` timestamp DEFAULT now(). New server actions: `captureDeckSnapshot(deckId)` serializes current deck state via the existing `exportDeck` path and inserts a row (then trims to keep only the 5 most recent for that deck in the same transaction — hard cap); `loadDeckSnapshots(deckId)` returns the last 5 by `captured_at DESC`.
2. Call `captureDeckSnapshot` in four existing mutation paths in `app/actions.ts`: `addColumn`, `removeColumn`, `reorderColumns`, and `importDeck` (captures the pre-import state as a rollback point). Snapshots are fire-and-forget — a failed capture does not fail the mutation. No UI feedback on capture (autosave model: it happens silently, you see it only in version history).
3. "Version history" section in the Configure Deck dialog: list of up to 5 entries, each showing a relative timestamp ("3 hours ago", "yesterday") and a "Restore" button. Restore calls `importDeck` with the snapshot JSON (same DeckExport v1 Zod validation path, same `(restored)` rename suffix, same activate-as-new-deck contract). Uses the next available migration number for main (check `drizzle/meta/_journal.json` for the current sequence — PR #51 may have taken the next slot after #50's webhook migration). No new dependencies.
