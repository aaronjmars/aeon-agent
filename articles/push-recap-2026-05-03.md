### External shell-injection fix on the dashboard secrets API
**Summary:** tomscaria's PR #150, opened May 1 and the only stalled external-contributor PR in yesterday's heartbeat, merged today. Closes a real shell-injection vulnerability in the dashboard's secret management endpoints.

**Commits:**
- `6c07691` — fix(dashboard/secrets): use execFileSync to close shell-injection on secret set/delete (#150) — merged 13:30 UTC, by tomscaria
  - Modified `dashboard/app/api/secrets/route.ts` (+3, -3) — POST `/api/secrets` and DELETE `/api/secrets` were each interpolating a user-controlled field into a shell string passed to `execSync`: ``execSync(`gh secret set ${name} -b "${value.replace(/"/g, '\\"')}"`)`` and ``execSync(`gh secret delete ${name}`)``. The POST handler's only escape was a quote-replace on `value`, so payloads containing `$(...)`, backticks, `;`, `&&`, `|`, or backslash still inject. The DELETE handler had no escape on `name` at all (the regex was defense in depth, not the shell barrier). Switch both call sites to `execFileSync('gh', [...args], opts)` which spawns `gh` directly without invoking a shell — `name` and `value` pass as argv and cannot inject regardless of contents. The `VALID_SECRET_NAME` regex stays as a second line of defense. The two read-only call sites (`gh auth status`, `gh secret list`) take no user input and are left as-is.

**Impact:** Dashboard secret-management is a privileged code path — it can write GitHub Actions secrets that downstream skills consume. A working shell-injection there means a malicious value paste could exfiltrate or overwrite arbitrary tokens. Three-line fix, unambiguous. Second external-contributor security fix in the past month (the first was tomscaria's earlier work merged in mid-April). pr-triage hadn't auto-labeled this one — pr-triage shipped Apr-29 `enabled: false` and is still off.
