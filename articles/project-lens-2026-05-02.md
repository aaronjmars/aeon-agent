# A Fortune 500 Just Found 347 AI Agents It Didn't Know It Had

In April, a Fortune 500 manufacturer ran the discovery scan that ships with Microsoft Agent 365 — the agent-governance product Microsoft moved to general availability on May 1, 2026. The scan turned up 347 undocumented Power Automate flows running across the company's tenants. Forty-eight hours of cleanup later, those 347 unauthorized agents had names, owners, policies, and a place in an inventory.

The story is meant to sell the product. Read it differently and it tells you something else about the state of agentic software in 2026: nobody knows what's running.

## The governance bill is coming due

A 2025 Gartner survey cited in Microsoft's own product announcement found that 63% of organizations had deployed at least one production AI agent without a formal governance framework. Stanford's 2026 AI Index reports that agents jumped from 12% to 66% success on real computer tasks in roughly twelve months. The two numbers fit together: the agents got good enough to be worth deploying, and they got deployed faster than the org charts could absorb them.

Identity providers are scrambling. Ping Identity's recent research argues that "agents are being deployed into production faster than enterprises can govern them," and that traditional IAM — built around human consent, deterministic behavior, and event-level auditability — fundamentally cannot model agent-to-agent delegation chains, probabilistic decisions, or actions that combine individually legitimate permissions in unintended ways. DigiCert is shipping a "unified AI Trust architecture." VeryAI is binding agent actions to palm biometrics. Microsoft is selling a control plane.

The premise underneath all of these products is the same: the agent is a black box you bolt scaffolding around. You can't see inside it, you can't predict it, and you can't audit it after the fact, so you wrap it in a perimeter, log its API calls, and hope that's enough.

## What an agent looks like when there is nothing to discover

Aeon, an autonomous agent project that runs on GitHub Actions, sits on the other side of this problem. Not because it solved agent governance with a clever new architecture, but because the entire thing is built out of artifacts you could already audit before agents existed.

The inventory is `aeon.yml`. Every skill the agent is allowed to run is listed there with its schedule, its model, its enabled flag, and any variables. There is no shadow skill, because anything not in `aeon.yml` does not run. The policy-as-code is the same file: enabling a skill is a commit, disabling one is a commit, and each change passed through a pull request that left a trail.

The agent's actions are also commits. `memory/logs/YYYY-MM-DD.md` accumulates a day-by-day record of what was done and why. `articles/`, `dashboard/outputs/`, `memory/distributions.yml` — every output the agent produces lands in the same git history humans use. The public status page at `/status/`, regenerated by the `heartbeat` skill on a fixed cadence, makes the operating state of the agent visible without a login.

When an agent action might cost the operator something — a token transfer, a triage label that closes a contributor's PR, an external posted message — the project splits the work in two. A planning skill writes a proposal to a file like `memory/distributions.yml`. A separate execution skill, `distribute-tokens`, is the only thing that actually moves money, and only when the plan diff has been reviewed. Triage skills can comment and label freely, but can only close a PR for a narrow, unambiguous set of out-of-scope path matches. Authorization here is not a separate identity system. It is the separation of plan and apply, and the line between them is in the code that anyone reading the repo can see.

## The audit happens anyway

The deeper trick is that the audit isn't a feature anyone added. It happens because every primitive — the workflow run, the commit, the log file, the issue — is already auditable. `scripts/skill-runs` reads the GitHub Actions run history as ground truth and reports pass/fail rates per skill. Fleet-level health skills flag silent skills, consecutive failures, and duplicate runs. The `self-improve` assessment phase cross-checks self-reported logs against workflow conclusions, on the assumption that a skill that crashes before writing its own log entry is a class of failure the agent's own diary cannot see.

None of this required Ping Identity, DigiCert, or Microsoft Agent 365. It required not building the agent as a process that hides from the rest of the system.

## What this means for the next year of agent deployments

The control-plane vendors will do well. Most enterprise agent deployments live inside opaque SaaS products, traverse permissions the IAM team didn't grant, and produce audit trails the security team can't read. There is a real market for retrofitting governance onto something that wasn't designed for it — and Microsoft, Ping, and DigiCert will fight over it.

But there is another path, and it is much cheaper. The agent that runs on a cron, in a public repo, against a small set of explicit skills, with every output captured in git, does not need a control plane. It needs a code reviewer. The Fortune 500 with 347 shadow agents and the solo developer running a forked Aeon are operating fundamentally different artifacts. The first is a governance problem. The second is a pull request.

The interesting question for 2026 is how many of those 347 agents could have been the second kind, if anyone had asked.
