VIGIL Approval Revoker (vigil-revoke)
A new workflow_dispatch-only skill that revokes a single live ERC-20 approval on Base in one click. The operator passes a `wallet:spender:token` triplet — the same shape the existing read-only `vigil` and `approval-audit` skills already return — and the skill confirms the approval is still live, submits the on-chain revoke through Bankr, then waits for the receipt and re-reads the allowance to confirm. The notification only claims SUCCESS when the chain itself shows the allowance dropped to zero.

Why this matters:
VIGIL's PR #323 review explicitly split the Approval Revoker out into a separate future skill — the maintainer comment said "Bankr-gated, state-changing — separate PR." Then `wallet-risk-weekly` shipped on 2026-06-04 (PR #340) and started surfacing HIGH-bucket unlimited approvals every Monday. For the last three days, the agent has been telling the operator "you have an UNLIMITED approval to a non-trusted spender" with no autonomous path to act on it. This skill closes the loop: copy the triplet from the wallet-risk-weekly Telegram message, dispatch once, done.

What was built:
- `skills/vigil-revoke/SKILL.md`: New skill, 11 steps. Strict input regex `^0x[hex40]:0x[hex40]:0x[hex40]$` rejects everything except three colon-separated 40-hex addresses, then normalises to lowercase before any interpolation (mirrors the input hardening VIGIL adopted in review round 4). Bankr ownership pre-check via `/wallet/me` refuses any submission where the triplet wallet ≠ Bankr's bound wallet. Pre-revoke `allowance(owner,spender)` `eth_call` short-circuits to NOOP when the approval is already zero — no gas spent on a redundant submission. Post-revoke: receipt poll via `eth_getTransactionReceipt`, then a final allowance read so the notification only claims SUCCESS on chain-confirmed `0x000…000`. State logged to `memory/topics/vigil-revoke-log.json` (append-only, 500-entry cap).
- `aeon.yml`: Registered disabled at the end of the Hound onchain investigation section (after `holder-concentration`).
- `generate-skills-json`: Extended the `onchain-security` case line to include `vigil-revoke` alongside `vigil` and `wallet-risk-weekly`.
- `skills.json`: Regenerated — total 193 → 194, inserted alphabetically between `vigil` and `vuln-scanner`.

How it works:
The Bankr Wallet API doesn't have a direct ERC-20 `approve` endpoint, so the skill uses `/agent/prompt` (the same path `distribute-tokens` uses for natural-language wallet operations) with a tightly-controlled prompt that names ONLY the three validated 40-hex addresses — no operator-typed text, no fetched contract metadata, zero prompt-injection surface. Polling on `/agent/job/{id}` for up to 90 seconds (Base block time ~2s, so a clean revoke usually settles in one block), then `eth_getTransactionReceipt` on the returned tx hash. Capabilities declared: `external_api`, `writes_external_host`, `onchain_writes`, `sends_notifications` — matches the locked taxonomy in `docs/CAPABILITIES.md`. The skill exits through a 7-state taxonomy (OK / NOOP / FAILED / BAD_VAR / WALLET_MISMATCH / ERROR / STATE_CORRUPT) so log analytics can tell apart "already revoked" from "config error" from "submit failed".

What's next:
The detection→revoke loop is closed for single approvals. A future `vigil-revoke-batch` would handle multi-approval revocation in one run (deliberately out of scope here — keeps blast radius bounded). Five other HoundFlow security skills still have no scheduled consumer — natural pairing targets if a future skill wants to drive bulk action off their findings.
