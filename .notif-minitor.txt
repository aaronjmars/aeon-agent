*Feature Built — 2026-06-09 — aaronjmars/minitor*

Deck keyboard navigation shortcuts
Minitor now has a keyboard layer. With 10+ columns per deck becoming routine after the last two weeks of per-column UX work (tab groups, collapse, search, pin, duplicate, color, width, deck DnD), every action was hunt-and-click. Press j and k to move focus between columns, / to open the focused column's search bar, c to collapse it, Escape to clear. Mirrors the shortcuts operators have in muscle memory from Linear, GitHub issues, and most terminal dashboards.

Why this matters:
This is the 10th rung on the per-column UX axis in 11 days — and at this point the cognitive cost of finding a button on each column is the actual bottleneck, not the affordance on each column. Yesterday's repo-actions called this the next natural shortcut layer: a single keydown listener routes events to actions that already exist (toggleColumnCollapsed, setColumnSearch, the inline search-open UI). No new components, no DB fields, no migration — purely an ergonomic layer over the existing per-column surface. At 15 columns the difference between mouse-only and mouse+keyboard is roughly the difference between a Tweetdeck-era dashboard and a modern productivity tool.

What was built:
- lib/store/use-deck-store.ts: new focusedColumnId and pendingSearchOpen view-state-only fields (same lifetime as collapsedColumnIds/searchByColumn/widthByColumn), with setFocusedColumn/requestSearchOpen/clearPendingSearchOpen actions. Both fields scrubbed in deleteDeck + removeColumn so the listener can never operate on a stale id pointing at a deleted column
- components/deck/deck-board.tsx: a window keydown listener that routes j/ArrowRight (next, wraps), k/ArrowLeft (previous, wraps), / (request search open on focused), c (toggle collapse on focused), Escape (two-step: clear focused column's search query, then clear focus ring). Modifier keys (Ctrl/⌘/Alt) and text-editable elements (input/textarea/select/contenteditable) bypass the listener so ⌘K and typing in a search box are never intercepted. requestAnimationFrame(scrollIntoView) after j/k keeps the focus ring visible past horizontal scroll edges
- components/column/column-card.tsx: ring-2 ring-[color:var(--brand)]/60 on the focused column's wrapper on both the expanded and collapsed render paths. Click-to-focus handler on both wrappers so mouse + keyboard agree on what's selected. useEffect reacting to pendingSearchOpen === column.id opens the inline search row, focuses the input, then clears the signal so a subsequent / re-fires cleanly

How it works:
The deck-board listener reads visibleColumnIds — the same pinned-first tab-filtered array SortableContext renders — so j/k walk the columns in the order the operator sees, not the raw columnIds order. pendingSearchOpen is a column id (not a boolean) so a fast j/j/ sequence lands on the second column's search box, not the first. Escape is two-step: when a column is focused and has an active search query, the first press clears the query (matching what the column's own Esc handler already does inside the input), the second press clears the focus ring entirely — lets the operator stay on a column while exiting search mode. The / shortcut is a no-op when nothing is focused, by design: pressing / first then j would surface a search bar on a column the operator hadn't picked.

What's next:
The bottleneck is now likely cross-deck (switching between decks via keyboard) and column-action depth (rename/configure/delete via keyboard). Both are natural follow-up rungs.
